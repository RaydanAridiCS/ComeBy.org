# 0016: Migrations run when the server starts

**Status:** accepted · recorded 2026-11-15 (the decision was made earlier, during the build)

## Context
One person deploys Comeby, by pushing to `main`. A separate "run migrations" step is easy to forget, and a deploy whose code expects a column that isn't there yet fails in confusing ways.

## Decision
`src/instrumentation.ts` runs `runMigrations()` (`src/db/migrate.ts`) when the Node.js server starts, before the background workers start. It applies every pending SQL file from `drizzle/`, which is copied into the Docker image.

- If the database isn't reachable, it retries five times with growing pauses, then fails startup.
- Migration files are generated by `drizzle-kit generate` and committed. A committed migration is never edited. CI regenerates and fails if the schema and `drizzle/` disagree.
- `SKIP_STARTUP_TASKS=1` skips it, for the build stage and for tooling.

## Consequences
- A deploy is one step, and the app never serves requests against an older schema than it expects.
- The app's database user needs permission to change the schema.
- Startup is as slow as the slowest pending migration. A long data migration would delay a deploy and should be done some other way.
- Migrations only go forward. Rolling back to the previous image leaves the new schema in place, so migrations must be written to keep the previous version working (add first, remove a release later).
- This assumes a single instance. Several instances starting together would each try to migrate at the same moment, which this setup has not been designed or tested for.
- `repairLegacyThemes()` runs after every migration pass. It exists because an early version of migration 0001 was edited after being applied, which is the mistake the rule above now prevents.
